# Firestore Data Model — Personal Gemini Journal + Knowledge Companion

Companion to `docs/architecture.md`. Defines the finalized Firestore schema, ownership, authorities, and indexes. **All access is server-side** (see architecture §7); clients have zero Firestore access (Security Rules deny all).

Conventions:
- Field types: Firestore types (`string`, `int`, `float`, `bool`, `timestamp`, `map`, `array`, `reference`, `geopoint`).
- All `id` fields are Firestore document IDs (auto-generated, opaque).
- All timestamps are Firestore server timestamps (`SERVER_TIMESTAMP`) set by the backend.
- **Read/write authority** refers to the backend repository methods, keyed by the verified Firebase `uid`. Clients: none.

---

## 1. Collection tree

```
users/{userId}
├── profile/{userId}                 (mirror doc, auto-created)
├── conversations/{conversationId}
│   └── messages/{messageId}
│   └── summaries/{summaryId}
├── resources/{resourceId}
├── knowledge/{knowledgeId}
└── recommendations/{recommendationId}
```

Explicitly NOT used (proposal in the brief, rejected after evaluation): top-level `conversations/`, `summaries/`, `resources/`, `knowledge/` collections, and `learningPath/` (merged into `knowledge` + optional `progress`).

**Evaluation of the proposal:** top-level collections would require every document to carry an `ownerUid` field and every query to filter on it — a classic source of cross-user leakage and of Security-Rules complexity. The `users/{uid}/…` tree makes ownership a property of the path itself: no field to forge, no filter to forget. Trade-off: no collection-group/global queries (none needed in the MVP). Firestore deep-path limits are not a concern at this scale (subcollection depth here is 2 levels).

## 2. users/{userId}/profile/{userId}

| Field | Type | Req | Description |
|---|---|---|---|
| `email` | string | ✓ | Email from verified token (lowercased) |
| `displayName` | string | – | Optional display name |
| `createdAt` | timestamp | ✓ | First server contact |
| `lastSeenAt` | timestamp | ✓ | Last authenticated request |
| `settings` | map | – | Optional: `defaultMode`, `summaryInterval` override |

Ownership: user. Authority: backend auto-creates/updates on first request; no user-writable fields beyond settings (future). Indexes: none.

## 3. users/{userId}/conversations/{conversationId}

| Field | Type | Req | Description |
|---|---|---|---|
| `mode` | string | ✓ | `journal` \| `brainstorm` (locked enum) |
| `title` | string | ✓ | Auto-generated by Gemini from first message; editable ≤ 200 chars |
| `createdAt` | timestamp | ✓ | |
| `updatedAt` | timestamp | ✓ | Last message time (drives list order) |
| `messageCount` | int | ✓ | Total messages (user+assistant) |
| `lastSummaryAt` | timestamp | – | Set when a summary is persisted (summary trigger marker) |
| `lastSummaryMessageIndex` | int | – | Index of last message covered by a summary (rolling summary) |
| `summaryCount` | int | ✓ | Number of summaries saved |
| `status` | string | ✓ | `active` \| `archived` (default `active`) |

Ownership: user. Authority: backend create/list/get/delete (delete cascades to subcollections via batched deletes). Indexes: `users/{uid}/conversations` order by `updatedAt desc` (single-field, automatic). No composite index needed for MVP queries.

Relationships: 1 → N `messages`, 1 → N `summaries`.

## 7. users/{userId}/knowledge/{knowledgeId}

| Field | Type | Req | Description |
|---|---|---|---|
| `type` | string | ✓ | `concept` \| `insight` \| `question` \| `actionItem` \| `resource` |
| `topic` | string | ✓ | Topic label ≤ 100 chars |
| `title` | string | ✓ | ≤ 200 chars |
| `content` | string | ✓ | The knowledge body ≤ 4000 chars |
| `keywords` | array<string> | – | ≤ 10 (context retrieval matching) |
| `tags` | array<string> | – | ≤ 10 (user organization) |
| `sourceRef` | map | – | `{kind: conversation\|resource\|manual, id: <id>, excerpt?: string}` |
| `projectRelevance` | string | – | Free text ≤ 500 chars |
| `status` | string | ✓ | `pending` \| `approved` \| `rejected` |
| `createdAt` | timestamp | ✓ | |
| `updatedAt` | timestamp | ✓ | |

Ownership: user. Authority: backend create (manual → `approved`), list (filter by status), get, update (status + editable fields), delete. AI-extracted items enter as `pending`; only user approval promotes to `approved`. Indexes: list by `status` requires single-field index (automatic); context retrieval filters `approved` in-app after fetching latest N — **no composite index needed for MVP** (documented decision; upgrade path: add `(status, updatedAt desc)` composite if knowledge grows large).

## 9. Index requirements (complete list)

| Collection | Query | Index type | Needed |
|---|---|---|---|
| `conversations` | order by `updatedAt desc` | single-field | automatic |
| `summaries` | order by `createdAt desc` | single-field | automatic |
| `resources` | order by `createdAt desc` | single-field | automatic |
| `knowledge` | where `status == X` | single-field | automatic |
| `messages` | order by `messageIndex asc` | single-field | automatic |
| `recommendations` | order by `createdAt desc` | single-field | automatic |

**No composite indexes are required for the MVP.** All queries are single-scope (`users/{uid}/…`) with single-field ordering. If knowledge grows, add `(status, updatedAt desc)` — documented as an upgrade, not a current requirement. Emulator tests will catch any missing-index errors during development; composite indexes, if added later, are declared in `firestore.indexes.json`.

## 10. Query patterns by feature

| Feature | Queries (all `users/{uid}/…`) |
|---|---|
| Dashboard | conversations (top 20 by updatedAt), resources (top 10), knowledge count, pending knowledge count |
| Chat | conversation doc + latest summary (1) + last 10 messages by messageIndex |
| Summarize | messages since lastSummaryMessageIndex (range read) |
| Context retrieval | knowledge (latest 30 approved, keyword match in-memory), resources (latest 30 completed, keyword match) |
| Recommendations | latest summary, latest 10 knowledge, latest 10 resources |

All reads are bounded (≤ 50 docs) — Firestore cost per read is trivial at this scale; the bounded-context strategy in `ai-architecture.md` keeps Gemini cost dominant-but-capped.

---

## 11. Write amplification & cost notes

- Every chat turn = 2 doc writes (user + assistant message) + 1 conversation update. ~10 turns/day/user → trivial.
- Summary = 1 doc per 6 messages (rolling).
- Resource = 1 doc + analysis update.
- Firestore free tier (per day): 50k reads / 20k writes / 20k deletes — ample for the Ideathon demo and judging; keep optional features lean to stay under.

---

## 12. Deletion semantics

- `DELETE /api/v1/conversations/{id}` and `/api/v1/resources/{id}`, `/api/v1/knowledge/{id}` → server deletes the doc plus subcollections (messages/summaries) in batched deletes (up to 500 ops per batch; loop batches if needed).
- No GDPR-style full-account purge endpoint in MVP (documented; `firebase auth delete` + manual collection deletes via a maintenance script if required by judges).
